# Черновик PRD: Wordstat Media Planner / Yandex Site Checker 2.0

## 1. Краткое описание продукта

Нужно разработать и поддерживать веб-скрипт, который помогает быстро собрать первичный медиаплан по нише и региону на основе данных Яндекс Wordstat. Пользователь вводит нишу, регион, опционально месячный бюджет и цель рекламной кампании, а сервис автоматически запрашивает частотность ключевых фраз, ранжирует запросы по приоритету, считает базовую сводку и показывает результат на отдельной странице сайта.

Продукт должен быть простым для запуска на сервере, понятным для неразработчика и достаточно надежным для интеграции с внешними формами, например Tilda. Основной сценарий — быстро открыть страницу отчета, которую можно отправить клиенту ссылкой или использовать как стартовую точку для SEO/контекстной рекламы.

## 2. Цель проекта

Сделать легкий backend-first инструмент для автоматической подготовки медиаплана без ручного копирования данных из Wordstat.

Основные цели:

- сократить время подготовки первичного медиаплана до нескольких минут;
- использовать только реальные данные Wordstat API как источник частотности;
- обеспечить простой web-интерфейс для менеджера или маркетолога;
- показывать отчет на отдельной web-странице с понятной структурой: входные данные, список ключей, частотность, приоритет, агрегированные метрики;
- оставить основу для будущего расширения: CRM, Tilda, хранение лидов, история отчетов, улучшенная аналитика, экспорт в XLSX/Google Sheets.

## 3. Для кого делаем

### Основные пользователи

1. **Маркетолог / performance-специалист**
   - быстро оценивает спрос по нише и региону;
   - готовит первичный медиаплан для клиента;
   - хочет видеть частотность и приоритеты без ручной обработки.

2. **Менеджер по продажам агентства**
   - получает заявку с сайта или Tilda;
   - вводит нишу и регион;
   - скачивает PDF и прикладывает его к коммерческому предложению.

3. **Владелец малого бизнеса / подрядчик**
   - хочет понять примерный спрос в Яндексе;
   - получает простой отчет без сложных рекламных кабинетов.

## 4. Что это будет за скрипт

Это веб-приложение на FastAPI, которое работает как небольшой сервис:

1. показывает HTML-форму;
2. принимает данные пользователя;
3. валидирует поля;
4. обращается к Wordstat API;
5. нормализует ответ API;
6. сортирует ключевые фразы по частотности;
7. присваивает приоритеты;
8. при наличии бюджета распределяет бюджет по группам приоритета;
9. сохраняет результат и формирует публичную/временную ссылку на страницу отчета;
10. переводит пользователя на страницу отчета или отдает ссылку, если сценарий запускается через webhook.

Дополнительно сервис принимает webhook от Tilda. Важно: webhook Tilda обычно является server-to-server вызовом, поэтому сам ответ webhook не может напрямую перенаправить браузер пользователя на страницу отчета. Рабочие варианты: настроить в Tilda страницу успеха/redirect на URL нашего сервиса, если Tilda позволяет передать идентификатор заявки; заменить стандартную форму Tilda на форму, которая отправляет пользователя напрямую в наш backend; или после webhook показывать пользователю стандартную страницу Tilda, а ссылку на отчет отправлять менеджеру/клиенту отдельно. В PRD целевой вариант — после заявки пользователь попадает на `/reports/{report_id}`, но реализация зависит от возможностей формы Tilda.

## 5. Оптимальный стек

Для текущего размера проекта лучший стек — простой Python backend без тяжелого frontend-фреймворка.

### Backend

- **Python 3.11+** — стабильная версия с хорошей поддержкой типизации и async-кода.
- **FastAPI** — быстрый backend-фреймворк, удобен для форм, API endpoints, webhook и будущей OpenAPI-документации.
- **Pydantic / pydantic-settings** — валидация входных данных и настройка приложения через `.env`.
- **httpx.AsyncClient** — асинхронные HTTP-запросы к Wordstat API.
- **Jinja2** — серверные HTML-шаблоны для простой формы без сборки frontend.
- **ReportLab** — опциональный экспорт PDF на следующих этапах; в основном MVP результат показывается как HTML-страница.

### Хранение данных

Для сценария со страницей отчета нужна база данных, потому что результат должен быть доступен по ссылке после webhook. Для MVP допустима SQLite, для production лучше заложить PostgreSQL:

- **SQLite** для MVP и локального хранения отчетов/лидов;
- **PostgreSQL** для production-версии, если появятся пользователи, история отчетов, роли и интеграции.

### Frontend

- **HTML + CSS + Jinja2** — достаточно для MVP: форма, ошибки, базовые состояния.
- Без React/Vue на первом этапе, чтобы не усложнять деплой.
- Если появится личный кабинет, история отчетов и интерактивные таблицы — можно перейти на **React + TypeScript + Vite**.

### Инфраструктура

- **Uvicorn** как ASGI-сервер.
- **systemd** или простой deploy-скрипт для production-запуска.
- **cron-based auto update** как временное решение для небольшого сервера.
- **Docker Compose** стоит добавить на следующем этапе, чтобы унифицировать запуск приложения, базы и reverse proxy.
- **Nginx + HTTPS** для публичного сервера и приема webhook от Tilda.

### Качество кода

- **pytest** для unit/integration-тестов.
- **ruff** для линтинга.
- **black** для форматирования.
- Typed models и сервисный слой, чтобы бизнес-логика не расползалась по routes.

## 6. Основные пользовательские сценарии

### Сценарий 1. Генерация медиаплана через форму

1. Пользователь открывает главную страницу `/`.
2. Видит форму с полями:
   - ниша;
   - регион;
   - месячный бюджет;
   - цель кампании.
3. Заполняет обязательные поля: ниша и регион.
4. Нажимает «Сформировать медиаплан».
5. Backend валидирует данные.
6. Backend запрашивает Wordstat API.
7. Backend получает список популярных запросов по нише и региону.
8. Сервис строит медиаплан.
9. Сервис сохраняет отчет и создает `report_id`.
10. Пользователь открывает страницу `/reports/{report_id}` с результатом.

### Сценарий 2. Ошибка Wordstat API

1. Пользователь отправляет форму.
2. Wordstat API возвращает ошибку, таймаут, 429 или ошибку авторизации.
3. Backend показывает понятное сообщение на странице.
4. Пользователь не видит traceback и технические детали.
5. Ошибка логируется для разработчика.

### Сценарий 3. Проверка webhook Tilda

1. Tilda отправляет `POST /webhook/tilda` с `test=test`.
2. Backend отвечает `200 OK` и телом `ok`.
3. Если приходит обычная заявка, backend логирует ключи payload и также отвечает `ok`.
4. В следующей версии payload можно будет сохранять в базу и связывать с генерацией отчета.

## 7. Логика работы сервиса

### 7.1. Валидация входных данных

Входная модель должна гарантировать:

- `niche` не пустая, длина от 2 до 200 символов;
- `region` не пустой, длина от 2 до 200 символов;
- `monthly_budget` опциональный, но если указан — больше 0;
- `campaign_goal` опциональная, длина до 500 символов.

Если данные некорректны, пользователь получает ошибку валидации.

### 7.2. Получение региона

Wordstat API ожидает ID региона, поэтому сервис должен:

1. получить справочник регионов через `/v1/getRegionsTree`;
2. развернуть дерево регионов в словарь `название региона -> regionId`;
3. найти регион пользователя без учета регистра;
4. если регион не найден — вернуть понятную ошибку.

Справочник регионов нужно кешировать в памяти процесса, чтобы не дергать API на каждый запрос.

### 7.3. Получение ключевых фраз

После определения региона сервис вызывает `/v1/topRequests` с параметрами:

- `phrase` — ниша пользователя;
- `regions` — массив с ID региона;
- `devices` — `all`;
- `numPhrases` — до 200 фраз.

Ответ API нужно привести к внутренней структуре:

- `phrase` — текст ключевой фразы;
- `frequency` — частотность;
- `match_type` — источник/тип, например `topRequests`.

Невалидные элементы ответа пропускаются. Если после фильтрации нет валидных ключей, сервис возвращает ошибку.

### 7.4. Построение медиаплана

Алгоритм MVP:

1. отсортировать фразы по частотности по убыванию;
2. присвоить приоритет:
   - `high`, если частотность от 10 000;
   - `medium`, если частотность от 1 000 до 9 999;
   - `low`, если частотность меньше 1 000;
3. посчитать:
   - количество ключей;
   - суммарную частотность;
   - среднюю частотность;
4. если пользователь указал бюджет, распределить его пропорционально суммарной частотности групп `high`, `medium`, `low`.

Важно: это не финальный рекламный прогноз, а первичная оценка спроса. В PRD и интерфейсе стоит явно объяснить, что расчет бюджета является ориентировочным.

### 7.5. Страница отчета

Страница отчета должна включать:

- заголовок отчета;
- нишу;
- регион;
- бюджет;
- цель кампании;
- дату создания;
- таблицу ключевых фраз;
- частотность;
- тип соответствия/источник;
- приоритет;
- сводные метрики;
- примечание, что данные получены через Wordstat API.

PDF-экспорт можно оставить как дополнительную функцию, но основной acceptance-критерий MVP — корректная HTML-страница отчета.

## 8. Нефункциональные требования

- Сервис должен отвечать на `/` HTTP 200 при нормальном запуске.
- Ошибки внешнего API не должны ронять приложение.
- Таймаут Wordstat API должен быть настраиваемым через `.env`.
- Токены и секреты нельзя хранить в коде.
- Логи должны помогать понять, какой endpoint и внешний API вызвались, но не должны печатать OAuth-токен.
- HTML-страница отчета должна корректно отображать кириллицу и быть адаптивной для desktop/mobile.
- Если включен PDF-экспорт, PDF должен корректно отображать кириллицу.
- Код должен быть покрыт тестами для успешного сценария, ошибок API, webhook и критичных утилит.

## 9. MVP-scope

В первую версию входит:

- главная HTML-форма;
- endpoint `POST /generate`;
- интеграция с Wordstat API;
- кеширование справочника регионов в памяти;
- расчет приоритетов и базовых метрик;
- генерация web-страницы отчета;
- хранение отчета и заявки хотя бы в SQLite;
- webhook `/webhook/tilda` и legacy endpoint `/lead/seo`;
- базовые тесты;
- README с инструкцией запуска.

Не входит в MVP:

- личный кабинет;
- авторизация пользователей;
- онлайн-оплата;
- полноценная CRM;
- сложный прогноз CPC/CPA;
- автоматическая отправка PDF на email;
- админ-панель;
- фронтенд на React.

## 11. Как разработчику работать с проектом

1. Создать виртуальное окружение.
2. Установить зависимости из `requirements.txt`.
3. Создать `.env` и указать `WORDSTAT_OAUTH_TOKEN`.
4. Установить DejaVu-шрифты для PDF с кириллицей.
5. Запустить приложение через Uvicorn.
6. Проверить `/`, webhook Tilda и открытие страницы отчета.
7. Перед изменениями запускать тесты.
8. Для новой бизнес-логики добавлять тесты в `tests/`.
9. Не смешивать route handlers и бизнес-логику: обработчик должен принимать запрос, сервис — считать, отдельный клиент — ходить во внешний API.

Рекомендуемая структура ответственности:

- `app/main.py` — routes и HTTP-обработка;
- `app/schemas.py` — входные и выходные модели;
- `app/services/wordstat_client.py` — интеграция с Wordstat API;
- `app/services/media_plan.py` — бизнес-логика медиаплана;
- `app/services/pdf_export.py` — генерация PDF;
- `templates/` — HTML;
- `static/` — CSS;
- `tests/` — автотесты.

## 12. Риски и важные замечания

- Wordstat API может ограничивать квоты, поэтому нужно корректно обрабатывать 429.
- Названия регионов могут не совпадать с пользовательским вводом, значит позже полезно добавить autocomplete или справочник регионов в интерфейсе.
- PDF-генерация зависит от наличия шрифтов на сервере.
- Распределение бюджета в MVP является эвристикой, а не гарантированным медиапрогнозом.
- При публичном доступе обязательно нужен HTTPS, особенно для Tilda webhook.

## 13. Критерии готовности MVP

MVP можно считать готовым, если:

- главная страница открывается;
- заявка из формы/Tilda содержит нишу и регион;
- при валидном Wordstat OAuth-токене создается отчет и доступна страница `/reports/{report_id}`;
- ошибки API показываются пользователю понятным текстом;
- webhook Tilda отвечает `ok` на тестовый payload;
- Docker-контейнер собирается и проходит healthcheck;
- тесты проходят локально на Unix и запускаются одной PowerShell-командой на Windows;
- README позволяет новому разработчику поднять проект без дополнительного объяснения.

## 14. Метрики успешности

### Продуктовые метрики

- Доля заявок, по которым отчет успешно создан: целевое значение для MVP — не ниже 95% при корректном токене Wordstat.
- Время от отправки заявки до готовой страницы отчета: целевое значение — до 10 секунд для обычного запроса до 200 фраз.
- Доля пользователей, открывших страницу отчета после заявки: целевое значение зависит от способа интеграции Tilda; если redirect технически доступен — не ниже 80%.
- Количество отчетов, созданных менеджером/сайтом за день.
- Количество ошибок Wordstat API по типам: auth, rate limit, timeout, unexpected response.

### Технические метрики

- `GET /` возвращает HTTP 200.
- `POST /webhook/tilda` возвращает HTTP 200 для тестового payload.
- `GET /reports/{report_id}` возвращает HTTP 200 для существующего отчета и HTTP 404 для неизвестного ID.
- Docker healthcheck проходит после запуска контейнера.
- Автотесты проходят в CI/local окружении.
- Время cold start контейнера — до 30 секунд на VPS начального уровня.

## 15. API и внешние зависимости

### Wordstat API

Используется официальный API Яндекс Wordstat:

- базовый URL по умолчанию: `https://api.wordstat.yandex.net`;
- получение дерева регионов: `POST /v1/getRegionsTree`;
- получение популярных запросов: `POST /v1/topRequests`;
- авторизация: OAuth bearer token в заголовке `Authorization`.

Ссылка на документацию Яндекса должна быть закреплена в README или отдельном техническом документе после финального выбора версии API. В коде нельзя хардкодить токен; он передается через `.env` как `WORDSTAT_OAUTH_TOKEN`.

### Tilda webhook

Используются endpoints:

- `POST /webhook/tilda` — основной webhook;
- `POST /lead/seo` — legacy endpoint для совместимости.

Ограничение: webhook не является надежным способом перенаправить браузер пользователя, потому что запрос обычно делает сервер Tilda, а не браузер клиента. Если нужен именно автоматический переход пользователя на отчет, разработчику нужно проверить один из вариантов:

1. Tilda success redirect на URL нашего приложения после отправки формы.
2. Передача ID заявки/транзакции из Tilda в redirect URL.
3. Кастомная форма вместо стандартной Tilda-формы, которая отправляет данные сразу в наш backend и получает HTTP redirect.
4. Асинхронный сценарий: webhook создает отчет, а ссылка отправляется по email/Telegram/CRM.

## 16. Где и в каком масштабе будет использоваться

MVP рассчитан на малый production:

- один VPS на Unix/Linux;
- 1 контейнер приложения;
- SQLite для первых запусков или PostgreSQL при росте;
- до нескольких десятков/сотен отчетов в день;
- один публичный домен с HTTPS через Nginx/reverse proxy;
- один или несколько источников заявок Tilda.

Если нагрузка вырастет, нужно вынести генерацию отчетов в очередь задач и заменить SQLite на PostgreSQL.

## 17. Docker-сборка и запуск

Проект должен собираться в Docker-контейнер:

```bash
docker compose build
docker compose up -d
```

Ожидаемый результат:

- контейнер слушает порт `8000`;
- healthcheck проверяет `GET /`;
- переменные окружения берутся из `.env`;
- данные, которые должны переживать перезапуск, монтируются в `./data`.

Для ручного запуска без Docker предусмотрены скрипты:

- `scripts/start.sh` — создать venv, установить зависимости и запустить Uvicorn в фоне;
- `scripts/stop.sh` — остановить процесс по PID-файлу или порту;
- `scripts/install_vps_unix.sh` — установить системные зависимости, собрать Docker и зарегистрировать systemd service на VPS;
- `scripts/run_tests_windows.ps1` — подготовить venv и запустить тесты на Windows.
